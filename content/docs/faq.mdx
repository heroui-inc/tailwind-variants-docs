# Frequently Asked Questions (FAQ)

import { Callout } from 'fumadocs-ui/components/callout';

## v3.3.0 Migration

### What's new in v3.3.0?

v3.3.0 introduces several major improvements:

1. Fully rewritten in TypeScript with stronger types
2. Conflict resolution included in the default build — no `tailwind-merge` install required
3. Performance improvements

See the [Release Notes](/docs/release-notes) for full details.

### Do I still need to install `tailwind-merge`?

**No** — not for Tailwind Variants. Conflict resolution is included in the default build. Keep `tailwind-merge` only if your app still calls it directly (`twMerge`, `extendTailwindMerge`, etc.).

## v3 Migration

### What's new in v3?

v3 introduces several major improvements:

1. **Two build options**: Default (with conflict resolution) and Lite (without merge)
2. **Massive performance improvements**: Up to 500x faster when using conflict resolution
3. **Enhanced `cn` utility**: Now supports functionality similar to `classnames`/`clsx`
4. **New `cx` function** (v3.2.0+): Lightweight utility without conflict resolution
5. **`cn` defaults to conflict resolution** (v3.2.0+): `cn` now merges by default in the default build

### Should I use the default build or lite build?

**Use the default build if:**

- You need automatic Tailwind CSS conflict resolution (no extra package required)
- Performance with conflict resolution is important (v3 is 400-500x faster)

**Use the lite build if:**

- Bundle size is critical (~80% smaller)
- You don't need automatic conflict resolution
- You handle class merging manually

### How do I migrate from v2 to v3?

For most users on **v3.3.0+**, just install / upgrade `tailwind-variants` — no `tailwind-merge` required:

```bash
npm install tailwind-variants
```

If you want to use the lite build instead:

```ts
// Change your imports from:
import { tv } from 'tailwind-variants';
// To:
import { tv } from 'tailwind-variants/lite';
```

### What happened to lazy loading in v3?

v3 removes lazy loading of conflict resolution in favor of two separate builds. This fixes issues where classes wouldn't merge correctly on first render. The default build includes conflict resolution; the lite build does not.

### Should I replace `cnBase` with `cx`? (v3.2.0+)

Yes! In v3.2.0+, `cnBase` should be replaced with `cx`. The `cx` function provides the same functionality (simple concatenation without conflict resolution) with a clearer name.

**Migration example:**

```ts
// Before (v3.1.1 and earlier)
import { cnBase } from 'tailwind-variants';
{
  cnBase('flex items-center justify-center gap-2', className);
}

// After (v3.2.0+)
import { cx } from 'tailwind-variants';
{
  cx('flex items-center justify-center gap-2', className);
}
```

The API is identical - both functions combine class names without conflict resolution. `cnBase` is still exported for backwards compatibility, but `cx` is the recommended replacement.

### What's the difference between `cx`, `cn`, and `cnMerge`? (v3.2.2+)

There are three utility functions for concatenating class names, each serving different purposes:

**`cx`** - Lightweight utility without conflict resolution:

- Available in both default and lite builds
- Simply concatenates class names without merging conflicts
- Smaller bundle size
- Use when you don't need conflict resolution

```ts
import { cx } from 'tailwind-variants';
cx('text-blue-500', 'text-red-500'); // => "text-blue-500 text-red-500" (both included)
```

**`cn`** - Full-featured utility with conflict resolution (default build):

- Resolves conflicting Tailwind classes with the default config
- Returns a string directly (v3.2.2+)
- Use for the common case when you need conflict resolution

```ts
import { cn } from 'tailwind-variants';
cn('text-blue-500', 'text-red-500'); // => "text-red-500" (conflict resolved)
```

**`cnMerge`** - Configurable utility with conflict resolution (default build only):

- Supports custom merge configuration via second function call
- Not exported from `/lite`
- Use when you need to customize merge behavior (disable it or provide custom config)

```ts
import { cnMerge } from 'tailwind-variants';
cnMerge('px-2', 'px-4')({ twMerge: false }); // => "px-2 px-4" (no conflict resolution)
cnMerge('px-2', 'px-4')(); // => "px-4" (with default config)
```

**When to use each:**

- Use `cx` when you don't need conflict resolution and want a smaller bundle
- Use `cn` when you need automatic Tailwind CSS conflict resolution with default config (most common case)
- Use `cnMerge` when you need to customize merge behavior (disable it or provide custom config)

## v2 Migration

### Why was tailwind-merge optional in v2?

In v2, `tailwind-merge` was made an optional peer dependency to give users more control over their bundle size. Not all projects need automatic conflict resolution, and by making it optional, users who don't need this feature can save significant bundle size.

> **Superseded in v3.3.0:** Conflict resolution is included in the default build — you no longer need to install `tailwind-merge` for Tailwind Variants.

### Do I need to install tailwind-merge separately?

**On v3.3.0+:** No, not for Tailwind Variants. Keep it only if your app still calls `twMerge` / `extendTailwindMerge` directly.

**On v2 / earlier v3:** Yes, if you wanted automatic conflict resolution (enabled by default), you needed to install `tailwind-merge` as a peer dependency. Alternatively, set `twMerge: false` or use the lite build.

### How much faster is v2 compared to v1?

v2 is **37-62% faster** for most operations. The performance improvements come from:

- Optimized object creation and array operations
- Reduced function call overhead
- Better memory management
- More efficient class merging algorithms

## Common Issues

### Why are my Tailwind classes not being applied correctly?

This usually happens when:

1. **Conflict resolution is disabled**: Make sure `twMerge` is set to `true` (default on the default build), or that you are not importing from `/lite` if you need merge
2. **Class order matters**: Later classes in your variants override earlier ones
3. **Specificity issues**: Custom classes passed via `class`/`className` prop will override variant classes

### How do I override styles from a variant?

You can override styles in several ways:

```js
// Using the class prop
button({ color: 'primary', class: 'bg-pink-500' });

// Using compound variants
tv({
  variants: {
    /* ... */
  },
  compoundVariants: [
    {
      color: 'primary',
      size: 'large',
      class: 'bg-pink-500'
    }
  ]
});
```

### Why is TypeScript not inferring my variant types correctly?

Make sure you're using `as const` for your variant definitions if you're defining them outside of the `tv` function:

```ts
const variants = {
  color: {
    primary: 'bg-blue-500',
    secondary: 'bg-gray-500'
  }
} as const;

const button = tv({ variants });
```

## Performance

### Should I disable twMerge for better performance?

While disabling `twMerge` can provide a small performance boost, we recommend keeping it enabled unless:

- You're building a performance-critical application
- You're confident you won't have class conflicts
- You're already handling class merging manually

You can also use the lite build (`tailwind-variants/lite`) when merge is intentionally disabled globally.

### How can I optimize my tailwind-variants usage?

1. **Reuse tv instances**: Create tv components once and reuse them
2. **Avoid dynamic class generation**: Define all variants upfront rather than generating classes dynamically
3. **Use compound variants wisely**: They add overhead, so use them only when necessary

```js
// Good - defined once
const button = tv({
  /* ... */
});

// Avoid - creates new instance each render
function Component() {
  const button = tv({
    /* ... */
  });
}
```

## Usage Patterns

### Can I use tailwind-variants without React?

Yes! Tailwind Variants is framework agnostic. It works with any JavaScript framework or vanilla JavaScript:

```js
// Vanilla JS
const button = tv({
  /* ... */
});
document.getElementById('button').className = button({ color: 'primary' });
```

```vue
// Vue
<template>
  <button :class="button({ color: 'primary' })">Click me</button>
</template>
```

```svelte
// Svelte
<button class={button({ color: 'primary' })}>Click me</button>
```

### How do I handle responsive variants?

You can use Tailwind's responsive prefixes directly in your variant definitions:

```js
const component = tv({
  base: 'text-sm md:text-base lg:text-lg',
  variants: {
    color: {
      primary: 'text-blue-500 md:text-blue-600',
      secondary: 'text-gray-500 md:text-gray-600'
    }
  }
});
```

### Can I extend multiple components?

No, you can only extend one component at a time. However, you can compose multiple components manually:

```js
const baseButton = tv({
  /* ... */
});
const iconButton = tv({
  /* ... */
});

// Compose manually
const combinedButton = tv({
  base: [baseButton(), iconButton()]
  // additional variants...
});
```

### How do I use slots with TypeScript?

When using slots with TypeScript, you can extract the slot functions for better type inference:

```ts
const card = tv({
  slots: {
    base: 'p-4',
    title: 'text-lg font-bold',
    content: 'text-sm'
  }
});

// Extract with types
const { base, title, content } = card();

// Or use directly
<div className={card().base()}>
  <h1 className={card().title()}>Title</h1>
</div>
```
